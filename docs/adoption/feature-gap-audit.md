# Feature-Gap Audit — Path to Reception Adoption

_Generated 2026-06-27. Source: per-capability assessment + adversarial verification of 28 iHOTEL reception capabilities against the new app (Rust/Axum backend, Next.js classic + `/v2` frontends). Coverage values below are the **verified/revised** verdicts, not the original optimistic self-assessment._

## 1. Adoption-readiness summary

The new app is **verification-only and not yet usable for a single full reception shift**. Of the 28 reception capabilities audited, **zero have full coverage on both sites** — every one is partial, broken, or missing. The decisive blocker is money: **a receptionist cannot record a payment anywhere in the app** (the only `/payments`-posting UI, `components/modals/PaymentModal.tsx`, is orphaned, and the mounted `CheckOutModal` checks a guest out with an empty body and a note that says payment happens "in a separate menu" that does not exist). On top of that, the four other daily-critical flows (check-in, check-out settle, in-house folio, room board dispatch) are HF Hotel only and each omits core steps (deposit, signature, registration print, complete folio). HF Ville is structurally view-only across nearly the entire app: writes are blocked by `ville_write_guard` while `HFVILLE_WRITES_ENABLED` defaults off, and several read paths silently query the wrong pool. Several finished features sit dark behind flags (`CHECKOUT_SERVER_TOTAL_ENABLED`, `ROUND_WRITEBACK_ENABLED`, `AUTH_ENABLED`) or are fully built but unrouted (housekeeping service, customer edit/delete, redeem-coupon). In plain terms: reception must keep running iHOTEL for all real desk work today; the new app can show status and read history but cannot take money, check guests in/out with settlement, or operate HF Ville at all.

## 2. Top blockers (highest daily frequency, worst coverage first)

1. **Take Payment / Settle (high freq, BROKEN)** — no reachable UI records a payment; checkout captures no money. Backend + a complete modal both exist but the modal is unmounted. This single gap makes the app unusable as a PMS.
2. **Check-out & Settle (high freq, partial)** — the "check-out" half (status flip + writeback) works for HF Hotel; the "settle" half is unwired, the full folio is dark behind `CHECKOUT_SERVER_TOTAL_ENABLED`, and HF Ville checkout is unsafe (wrong-pool id collision).
3. **Walk-in / Check-in (high freq, partial)** — works for basic HF Hotel walk-ins but cannot record a deposit, capture signature/photo, read the ID card into the form, or print the registration slip; HF Ville check-in create does not exist.
4. **In-house Room Actions / Folio (high freq, partial)** — extend/change/checkout/POS work on HF Hotel, but there is no payment capture, no complete folio (room-only, no POS/payments/balance), and no stay notes; HF Ville gets none of it.
5. **Room Status Board / Rack (high freq, partial)** — the desk home screen displays live status for both sites, but it is a dispatch hub for HF Hotel only, omits reserve-from-cell and a working dirty/maintenance write, and has a real wrong-pool bug in the classic `/rooms` detail panel.

Cross-cutting blockers that gate many of the above: **HF Ville write parity** (off by default, several handlers ignore `?branch=`) and **shipped-dark / unrouted finished code**.

## 4. Already solid (full coverage on both sites)

**None.** No audited capability verified as full coverage on both HF Hotel and HF Ville. The closest are read/display paths that work for both sites but whose write/action half is partial or HF Hotel only:

- **Booking search** (find/modify/cancel) — fully present and branch-aware for reads; write half is HF Hotel only.
- **Room status board display** — live, server-derived, branch-aware on v2; but dispatch is HF Hotel only.
- **Shift/cash read reports** (`/api/shifts/{id}/report`, `/summary`) — genuinely printable and branch-aware for both sites; only the open/close write is dark/HF-Hotel.
- **Folio POS (charge to room)** — `classic=full`, `v2=full` for HF Hotel; sites limitation (Ville) keeps it from "full both sites".

## 5. Cross-cutting issues

These themes recur across the table and should be tackled as platform work, not per-feature:

- **HF Ville write parity is the single biggest multiplier.** `HFVILLE_WRITES_ENABLED` defaults off and `ville_write_guard` (`main.rs:592-621`) 403s every `?branch=hfville` mutation. Worse, many write services are bound to a single `new_pool` at wiring time (`mode.rs` `wire_services`) with **no Ville variant** — the referenced `resolve_write_services` is only a doc comment, so even flipping the flag would misroute Ville writes into the HF Hotel pool. Several **read** handlers also ignore `?branch=` and silently return HF Hotel data for a Ville selection (`get_room`, `get_invoice`, `get_customer_stats/bookings`, the income/occupancy reports, RR.4 export) — these are correctness bugs, not just gaps, because `cin_id`/`room_id` are per-DB SERIALs and can collide. Fix: a real per-site service/pool resolver threaded through every handler that takes `?branch=`, plus the Ship-B Ville write bundle.

- **Shipped-dark flags gate finished features.** `CHECKOUT_SERVER_TOTAL_ENABLED` (full folio), `ROUND_WRITEBACK_ENABLED` (round open/close), `BOOKING_VALIDATION_ENABLED` (overlap check), and `AUTH_ENABLED`/`NEXT_PUBLIC_AUTH_REQUIRED` (login + permissions + actor stamping) all default off in production. Each needs a validation pass (the checkout/payment ones touch live charges) and then a coordinated flip — this is cheaper than building, and unblocks settle, audit identity, and round control.

- **Finished-but-unrouted / orphaned UI.** Multiple complete code paths are unreachable: `PaymentModal` (payments), the richer `components/modals/CheckOutModal` (folio+tender), `HousekeepingService` + clean/dirty recipes, `update_customer`/`delete_customer` handlers, the redeem-coupon handler, `adjust_stock`/product CRUD, `get_pricing_reference`, and the `IssueCouponModal`/`GuestRegistryModal` modals. A focused "wire the dead code" sweep would lift several capabilities from broken/missing toward partial at low cost.

- **Actor / audit identity is not enforced.** Even with auth on, write handlers (`new_checkins.rs:738/933/1152`, `new_payments.rs:234`, `new_shifts.rs` opened_by/closed_by) leave actor blank or accept self-declared body text. iHOTEL's guarantee that every write is stamped with the logged-in employee does not yet hold; stamp from `Extension<User>` once auth is on.

- **Canonical-data completeness gates correctness.** Folio/total math falls back to `cin_rate_per_night.unwrap_or(0.0)` and deposit/refund display relies on inbound-sync-only columns (`cr_dep_*`). Where canonical PG rate is unpopulated, totals compute to 0. Before flipping `CHECKOUT_SERVER_TOTAL_ENABLED`, verify `cin_rate_per_night` (and POS/deposit lines) are populated for active stays on both sites.

- **No print artifacts for desk paperwork.** Registration slip, booking confirmation, daily guest rosters, VAT/tax invoice, room-change/coupon receipts — most of iHOTEL's `.rpt` outputs have no analog. `lib/print.ts` + `PrintButton` exist (used for round report, inventory, billing folio) and should be the reuse base for the missing documents.
