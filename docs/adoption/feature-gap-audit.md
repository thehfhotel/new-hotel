## 1. Adoption-readiness summary

**HF Hotel: approaching a parallel/shadow shift, not yet an unattended cash shift.** The full desk loop — check-in (+deposit, ID prefill, registration slip) → charge to room → take payment → check-out & settle → folio → tax invoice → daily rosters → round read — is built, reachable, and HF-Hotel-correct. Two things still stop it from running a real cash shift on its own: **(1)** payments hard-gate on an open `ht_shifts` round (`service/payment.rs:203-208`), and that row only arrives via iHOTEL round sync — the new app can't open a round (`ROUND_WRITEBACK_ENABLED` off), so it can only take payment while iHOTEL has an open round; **(2)** several new-app writes don't mirror back to iHOTEL (cash ledger outbound, sticky notes, pre-order products, waitlist bookings, round open/close all dark/unwired), so dual-write coexistence isn't complete. (Auth is NOT a blocker — it's fully done: prod backend runs `AUTH_ENABLED=true` (5 HF Hotel + 3 HF Ville users; session-less calls 401'd) AND the frontend has `NEXT_PUBLIC_AUTH_REQUIRED` baked true from the repo variable `AUTH_REQUIRED`, so forced-login + server-side actor-stamping + idle-logout are all live — verified 2026-06-29, #60 complete.)

**HF Ville: effectively read-only and not shift-ready.** Every write is 403'd by `ville_write_guard` (`HFVILLE_WRITES_ENABLED=false`). The resolver infra would route correctly if flipped, but ~8 handlers are still `new_pool`-bound and would **misroute Ville data into the HF Hotel DB** if the flag flipped as-is (folio-POS create/list, `checkout_quote`, coupons, round open/close, `list_guests`, `customer/search`, products, maintenance kanban). Compounding it, Ville canonical data is sparse: `ht_payments` = 0 rows, so Ville income/round reports render structurally-correct-but-empty.

## 2. Top blockers (highest leverage first)

1. **Payment ↔ open-shift coupling (HF Hotel, operational).** In-app payment 409s "no open shift" unless iHOTEL has an open round synced into `ht_shifts`; the new app can't open one. Either flip `ROUND_WRITEBACK_ENABLED` (after the reception-coordinated shift-boundary test, #61) so the app can open/close rounds, or relax the gate to a soft warning. This is THE blocker to the new app taking payment independently.
2. **HF Ville write parity (cross-cutting, the biggest multiplier).** `HFVILLE_WRITES_ENABLED` still off, but the ~8 flip-unsafe `new_pool`-only handlers are now **branch-safe** (commit `55f4ec8`, 2026-06-29 — folio-POS, checkout-quote, list-guests, coupons, round open/close, customer create+search, products, maintenance all route through `write_pool`/`resolve_write_services`; the Ville `ShiftService` binds `site_id='hfville'`). Remaining for #42: an e2e Ville-write test, then the coordinated flip. Unblocks nearly every Ville write capability at once.
3. **AUTH — DONE (#60 complete).** Backend (`AUTH_ENABLED=true`, 5 + 3 users, session-less calls 401) **and** frontend (`NEXT_PUBLIC_AUTH_REQUIRED` baked true from the GH repo variable `AUTH_REQUIRED`) are both live in prod, so forced-login redirect + server-side actor-stamping + idle-logout are all active. (Runtime `printenv` shows the frontend var unset — that's the build-time-inline trap, not evidence it's off.)
4. **Dark legacy-writeback paths (coexistence integrity).** New-app cash entries, sticky notes, pre-order products, waitlist bookings, and round open/close do not reach iHOTEL. Until wired, those new-app actions are invisible to the legacy app — unsafe for true dual-write. Each is flag-dark or recipe-unwired pending legacy byte-shape verification.
5. **Data completeness (verification gate).** `cin_rate_per_night=0` (mitigated by code fallback — verify folio parity before `CHECKOUT_SERVER_TOTAL_ENABLED`); Ville `ht_payments`=0; `ht_pos_sales`/`ht_cash_ledger`/`ht_booking_products` empty on both DBs. Built features are unexercised on real data — validate via read-only canonical-PG↔iHOTEL diff, not shadow logs.
